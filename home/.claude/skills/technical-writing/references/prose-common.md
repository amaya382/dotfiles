# Prose rules: language-independent

技術文書の文章規範のうち、言語に依存しないもの。日英どちらの文書でも読む。
言語固有の語彙と表記は `prose-ja.md` / `prose-en.md` にあり、この内容とは重複しない。

---

## 1. 主体と立場

**無生物を主語にして人間の動作をさせない。** 行為者か仕組みを主語にする。

| 避ける | 書き換え |
|---|---|
| このデータが物語る | 誰がデータを読んで何を結論したかを書く |
| 判断が生まれる | 誰が判断したかを書く |

**反証可能な主張まで降りる。** 「重要である」「本質的だ」で止めない。誰かが反論できる具体的な命題を書く。書けないなら、その文を消す。

**一般論で語らない。** 「多くの開発者は」は場面に踏み込んでいない。具体的な人・失敗・数値・固有名を伴わせるか、書かない。

## 2. 段落

- 一段落一話題。複数の主張が混ざったら分ける
- 議論は一方向に進む。結論を述べ、反論を処理し、また結論を述べ直す形にしない。反論を先に処理して、結論は一度だけ書く
- 節の末尾に次節の予告を置かない。節と節の橋は、次節の冒頭に問いや違和感として置く
- 読者が誤った推論をしそうなときは、正しい理由を述べる前にその推論を明示的に否定する
- 否定するときは、否定する命題を具体的に書く。曖昧に否定しない

## 3. 論証

- **因果を主張するなら仕組みを一文で述べる。** 「A が B をもたらす」だけでは足りない
- **異なるものを一つの語に潰さない。** 二つが違うなら、その違いを本文が認める
- **単一原因に還元しない。** 複数の要因があるなら分けて、それぞれが説明する範囲に対応させる
- **術語は load-bearing な使用より前に定義する**
- **緩和は検証状況に比例させる。** 本物の不確実性、他者の心的状態、反実仮想、読者が抱く疑念、未検証の情報には緩和を残す。本文自身の証拠が既に決着させた命題を無根拠に弱めない
  - 判定方法: 緩和を外して断定として読む。本文が証拠で決着させているなら緩和は弱めであり、外す。決着させていないなら緩和は正当であり、残す。迷ったら残す。誤った確信の方が悪い失敗である
- 検出・保証・解決が常に可能であるかのように書かない。条件を正確に述べる
- 挙げた例が主張の範囲全体を支えているか確認する。一部しか支えないなら、主張をその範囲に狭める
- 概念を複数まとめて一つの語で呼ぶときは、それらが同じ性質を共有することを一文で述べてから名前を与える

## 4. 階層と見出し

- **見出しの階層は従属を表す。** 順序でも強調でもない。親の話題の構成要素であるときだけ一段下げる。単に後に続くだけの節は同じ階層に置く
- 見出しが 1 つしかない階層は階層の誤り。親に統合するか、対になる兄弟を探す
- 3 階層が上限。4 階層目が要るなら、それは 1 文書に収まる量を超えている。分割する
- **見出しは名前であって主張ではない。** 結論を述べる文の形にしない
- **リストの兄弟は役割と粒度を揃える。** 同じ種類のもの (すべて原因、すべて手順、すべて選択肢) を同じ次元で並べる。具体的な補足は、それが修飾する親の下に入れ子にする
- 平坦なリストが 7 項目を超えたら、まとめていないグループが隠れている
- 兄弟の順序は意図的に決める (重要度、時系列、因果、使用頻度)。書いた順のまま残さない

## 5. 散文・リスト・表・図の選択

- **散文は論証を運ぶ。** 因果、譲歩、推論には接続が要る。順に読まないと意味が通らない項目は、リストの形をした段落である
- **リストは役割を共有する兄弟を示す。** 無関係な記述の羅列に使わない
- **表は二軸の比較を運ぶ。** 行が事例、列が属性。セルには短い事実を置き、解釈は周囲の散文に置く
- **図は、順に読むのではなく一度に把握すべき構造を運ぶ。** 二次元以上、状態機械、順序や並行性、境界の主張のいずれかがあれば図にする。3 つ以上の登場人物を鎖のように繋ぐ文は、図にすべき合図

**分担:** 図が構造を持ち、散文は理由・条件・図が描けないものを持つ。図を節ごとに言葉で辿り直さない。

**図の条件:**
- 一図一主張。一文で言える主張を持ち、その一文が caption になる。ただし全体像を示す図は、部分の関係そのものが主張なので分割しない
- すべての辺に条件か事象のラベルを付ける。節点の名前は散文の呼び方と揃える

**記法:** Mermaid を fenced block で inline に書く。レンダリング済み画像は併置しない。正確な空間配置や画面写真への注記が要るときだけ SVG にする。リポジトリの既存文書の形式が、この表より優先する。

| 内容の形 | Mermaid |
|---|---|
| 時間 × 登場人物、メッセージの順序 | `sequenceDiagram` |
| 状態 × 事象、許される遷移 | `stateDiagram-v2` |
| 境界 × 依存、何が何を含むか | `flowchart` + `subgraph` |
| 条件による分岐 | `flowchart TD` |
| 実体とその関係 | `erDiagram` |
| 期間と重なり | `gantt` |
| クラスや型の構造 | `classDiagram` |

## 6. 演出

- 演出装置 (溜め、反語、独立した一文の段落) は 1 節に 1 つまで
- 強調 (太字) は 1 節に 1〜2 箇所まで
- 転回点は事実の文で一度だけ述べる。帰結を積み重ねて繰り返さない
- 指すものが曖昧な比喩を避け、平易な動詞で書く
- **評価の強度を一段下げる。** 最大級 (「不可欠」「決定的」) ばかりで押さず、中程度の評価 (「妥当」「ばらつきがある」) を混ぜる。技術的に検証可能な事実 (API の挙動、アルゴリズムの性質、仕様の保証) は事実として断定し、緩和しない
- 「どちらにも良さがある」は判断の放棄である。選んだ方を選んだ理由とともに述べる
- 「場合による」で結論を回避しない

## 7. 例とコード

- 例は最小にする。含まれる要素すべてが主張を支えていること。余分な設定項目や 2 人目の登場人物は、読者になぜそれがあるのかを考えさせる
- 主要な例は典型的なものにする。特殊な例は後続に置き、特殊であると明示する
- どの主張を支える例なのかを、例の直前か直後に散文で述べる
- コードはそのまま動くか、省略を明示する (`...` かコメント)。効いてくる言語やバージョンの前提を書き、出力が要点なら出力を示す

## 8. 誠実さ

- 検証していないことを滑らかに書かない
- 例が作為的に見えそうなときは隠さない。読者が抱く疑いを認め、現実に起こりうる形で簡潔に根拠づける。その根拠づけは共有された経験や通念に置き、書き手の断言に置かない
