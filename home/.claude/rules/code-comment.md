# rules for code comments

- 既存のコードベースよりもこのルールを優先すること
  - ただしプログラミング言語ごとなどに独自のルールがある場合はそれも尊重すること

## 判断軸

- **既定はコメントを一切書かないこと**。命名・型・構造で伝わるなら、それで十分
- 書く前に、命名変更や関数抽出でコメントを不要にできないか先に検討すること
- コメントを消したとき、半年後の自分や新任の読み手が困るかどうかで書く価値を判断すること
- 過去の実装との差分に基づくのではなく、必ず今の実装に対して書くこと
- 現在の作業コンテキストを書くのではなく、コードベースをスナップショットとして読むときに必要となる情報を書くこと

## 書くべきとき

- コードから読み取れない「なぜ」を残すとき（何・どうやってはコードが語る）
- 非自明な制約や不変条件を明示するとき（順序依存、値の由来、スレッド安全性など）
- 特定の bug や外部仕様の癖を避ける workaround で、対応する issue や仕様書へ紐づけるとき
- 読み手が「これは変では」と感じる箇所を先回りして解くとき
- 境界の外との契約（呼び出し規約、副作用の範囲、事前・事後条件）を宣言するとき

## 書いてはいけないこと

- 命名で伝わる「何」の言い換え（例: `// increment counter`）
- 変更経緯や PR 番号・作業文脈（`git log` と PR description の役割）
- 呼び出し元・呼び出し先の列挙（コードを追えばわかり、変更に追従できず腐る）
- コミット済みコードを説明するだけの docstring 的な冗長注釈

## 書き方

- 基本的に英語としつつ、明らかに日本語で進行しているリポジトリに限り日本語で書くこと
- justification は最大 1 文に収めること
- 長い注釈が必要になったら、まず設計を見直すサインとして扱うこと
