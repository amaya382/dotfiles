# rules for code comments

- 既存のコードベースの慣習よりもこのルールを優先すること
  - ただしプログラミング言語などに固有の規約がある場合は、それも尊重すること

## 判断軸

- **既定はコメントを一切書かないこと**。命名・型・構造で伝わるなら、それで十分。
  - 既存のコメントを消すこともコードの改善として正当である。既存のコメントがあることを理由に残さないこと。
- 書く前に、命名変更や関数抽出でコメントを不要にできないか先に検討すること。
- コメントを消したとき、半年後の自分や新任の読み手が困るかどうかで書く価値を判断すること。

## 書くべきとき

- コードから読み取れない「なぜ」を残すとき（何をするか・どう実現するかはコードから読み取れる）
- 非自明な制約や不変条件を明示するとき（順序依存、値の由来、スレッド安全性など）
- 特定のバグや外部仕様の癖を避ける workaround を、対応する issue や仕様書に紐づけるとき
- 読み手が「これは変では」と感じそうな箇所で、その疑問に先回りして答えるとき
- 境界の外との契約（呼び出し規約、副作用の範囲、事前・事後条件）を宣言するとき

## 書いてはいけないこと

- 命名で伝わる「何」の言い換え（例: `// increment counter`）
- 変更経緯や PR 番号・作業文脈（`git log` と PR description が担う）
- 呼び出し元・呼び出し先の列挙（コードを追えばわかり、変更に追従できず腐る）
- コミット済みコードを説明するだけの docstring 的な冗長注釈

## 書き方

- 過去の実装との差分ではなく、必ず今の実装について書くこと
- 現在の作業コンテキストを書くのではなく、コードベースをスナップショットとして読むときに必要となる情報を書くこと
- 基本は英語で書き、明らかに日本語で運用されているリポジトリに限り日本語で書くこと
- 理由の説明は 1 文までに収めること
- 長い注釈が必要になったら、まず設計を見直すサインとして扱うこと

## 参考

- コードには How を、テストコードには What を、コミットメッセージには Why を、コードコメントには Why not を書く
